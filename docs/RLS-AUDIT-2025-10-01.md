# RLS & Index Audit – 01 Oct 2025

## Overview

This note tracks the latest audit of database security controls and performance protections for the med-mng platform.

## Methodology

- Reviewed every migration under `supabase/migrations/` to confirm:
  - `enable row level security` is executed for user-facing tables
  - `create policy` statements rely on `IF NOT EXISTS` to stay idempotent
  - Primary/foreign key pairs include supporting indexes when necessary
- Ensured the new deployment integrity registry uses restrictive policies with service-role write access only.
- Cross-checked high-traffic tables (`generated_tracks`, `lyrics_segments`, `study_notes`, `content_library_items`) for composite indexes and uniqueness guarantees.

## Findings

| Area | Status | Notes |
| --- | --- | --- |
| Row Level Security | ✅ | All public tables touched by users have RLS enabled and use `auth.uid()` / service-role gating. The new `deployment_integrity_*` tables restrict writes to the service role. |
| Policy Idempotency | ✅ | `create policy if not exists` pattern is consistent across migrations, preventing duplicate policy errors on re-apply. |
| Unique Constraints | ✅ | Critical tables expose primary keys + uniqueness: e.g. `generated_tracks(id uuid pk)`, `lyrics_segments(track_id, idx)` composite index, EDN sync run logs keyed by `(run_id)`. |
| Foreign Keys | ✅ | Cascading references exist for library collections, EDN sync runs, analytics events ➜ privacy preferences. |
| Performance Indexes | ⚠️ | Added explicit indexes for `deployment_integrity_snapshots` (environment/check). Future backlog: consider partial indexes on analytics tables once traffic grows. |

## Next steps

- Extend the integrity registry with checks covering Lighthouse budgets once QA flows stabilise.
- Automate this audit via a scheduled `pnpm postdeploy:check` run plus SQL checks in CI.
